repo-scraper

About

repo-scraper is a quiet way to understand the work behind a public GitHub profile. I made it to understand how a particular person is working, what they are building, how their projects are growing, which aspects of code they write, and what they have been working on over time.

It brings those public signals together into one clear overview: projects, languages, tools, README notes, repository structure, and visible activity. The result is useful for understanding a developer's public portfolio, following technical growth, comparing project directions, or preparing for a technical conversation.

The tool is intentionally focused on public repository information. It is not intended to identify, target, manipulate, impersonate, or socially engineer people.

Enter a GitHub username or organization and the tool collects:

  • Repository names and links
  • README files
  • File trees
  • Languages
  • Stars and forks
  • Topics, licenses, branches, and update dates
  • File counts, file types, and repository size estimates

It is useful for reviewing your own projects, preparing a portfolio overview, or doing respectful team and developer research from publicly shared work.

Optional GitHub token

Without a token, GitHub's API has a lower request limit. You can paste a personal access token into the token field while the application is running.

The token is used only for the current session and is not saved to the configuration file.

For normal repository metadata, the token does not need write permissions.

The application can export:

  • Markdown for readable notes or documentation
  • HTML for a searchable standalone report
  • Text clipboard dumps for quick sharing

Reports contain information retrieved from public GitHub repositories. README content and file paths are included, but source file contents are not downloaded.

Responsible use

Use this tool only with publicly available information and respect GitHub's terms, rate limits, and the privacy of repository owners.

The tool is intended for portfolio review, project discovery, learning, and legitimate team research. Do not use repository information to impersonate, target, manipulate, harass, or socially engineer people.

APK-Recon

Local-first Android reconnaissance. Point APK-Recon at an .apk and it turns the package into a reviewable security picture — endpoints and hosts, deep links, hardcoded secrets, SDKs, risky permissions, exported components, signing details, archive inventory and more — with graded, evidence-backed findings and a report you can hand over.

Everything runs on your machine. No uploads, no telemetry, no network access.

What it does

APK-Recon performs static analysis of an Android package and collects the things a security review actually needs:

  • Endpoints & infrastructure — URLs, hosts, domains, IPs, emails, file extensions, deep links,

query parameters and path prefixes.

  • Secrets & indicators — a ~40-category regex catalog (cloud keys, payment keys, tokens,

webhooks, private keys, wallets, generic credentials) plus high-entropy string candidates.

  • App surface — manifest flags, exported activities/services/receivers/providers, deep-link

routes, SDK/tracker fingerprints and platform hardening signals.

  • Build facts — APK inventory (DEX, native ABIs, assets, resources, largest entries), signing

schemes, certificate subject/issuer/SHA-256/expiry.

  • Judgement — severity-rated findings with evidence samples, a 0–100 risk score, an OWASP MASVS

posture report, a security checklist, and repeatable build-to-build diffs.

Results are searchable in the app and exportable as HTML, Markdown, JSON, CSV or plain text.

The problem it solves

Reviewing an APK manually is slow and easy to do inconsistently: unzip it, decompile it, grep through thousands of files, collect keys by hand, remember which manifest flags matter, translate all of that into MASVS language, and then write a report.

APK-Recon compresses that into a single pass with a consistent method:

  1. Find everything in one scan.
  2. Triage it with severity, risk and MASVS mapping.
  3. Prove it with evidence — the actual value, file, component or manifest attribute.
  4. Report it as a styled HTML page or Markdown, and compare it with the next build.

It is designed for authorized security testing, app hardening reviews, due diligence and CI-style regression checks — not for inspecting apps you do not have permission to assess.

Why it is useful

  • One window, no tool juggling — inventory, decompile, pattern scan, manifest/signing checks

and reporting are already wired together.

  • Evidence-first findings — every CRITICAL/HIGH/MEDIUM finding shows the value or attribute

that triggered it, plus its source file.

  • Prioritisation, not noise — weighted scoring, severity caps and MASVS coverage tell you what

matters first; entropy and informational items are clearly separated.

  • Repeatable across releases — local scan history plus baseline diff show exactly what changed

between builds.

  • Offline by design — nothing leaves the machine; no API keys, no cloud account, no telemetry.
  • Report-ready — a self-contained HTML report opens automatically after a scan (toggleable) and

can be regenerated at any time.

  • Fast and configurable — choose androguard/DEX-only, jadx or apktool; enable deep strings or

skip them; tune workers; reuse decompiled output.

  • Comfortable UI — dark and light themes, monospace layout, keyboard shortcuts, full-row

checkbox engine selection, instant search across every view.

How the analysis works

  • Pipeline — inventory → manifest/signing → extract (DEX or decompile) → parallel pattern scan →

scoring. UI updates are marshalled through after(); ETA is derived from completed work.

  • Extraction — URL schemes, domains, IPv4/IPv6, emails, extensions and a ~40-category secret

catalog, all compiled into regexes.py.

  • Entropy — tokens ≥ 24 chars with Shannon entropy ≥ 4.3, mixed letters/digits and ≥ 8 unique

characters; capped and deduped. Can be disabled (“Deep strings”) for speed.

  • Fingerprints — single-pass alternation regexes for 30+ SDK/tracker markers, weak crypto

markers and platform signals.

  • Manifest & signing — androguard reads flags, exported components and certificates

(subject/issuer/SHA-256/expiry, debug key detection, v1/v2/v3 presence).

  • Risk score — 100 minus weighted findings (CRITICAL 28, HIGH 14, MEDIUM 6, LOW 2), with

secret penalties capped at 45 and permission penalties at 25; grades A–F.

  • MASVS mapping — each category is scored from findings, manifest flags, signing data and

signals, with evidence bullets and official links.

  • Diff — set comparisons across URLs, domains, permissions, components, SDKs, secrets and

metadata.

  • History — last 100 scans stored in apk_recon_history.json; clearable from CONFIG.
  • Theming — two palettes (DARK, LIGHT); switching rebuilds the widget layer while keeping

the scan result, history, diff and filter intact.

What problem does it solve?

In a large microservice estate, security information is fragmented:

  • the SBOM knows which package versions are in a service;
  • a vulnerability feed knows which versions are unsafe;
  • a scanner knows which host is reachable from the internet;
  • an API document knows an endpoint has no authentication;
  • a secret scan knows a credential is exposed;
  • the CMDB knows which team owns the service;
  • management asks: how exposed are we, and what should we fix first?

Each tool answers a small question. ATLAS answers the combined question:

Which parts of the business are exposed, how badly, who owns them, and what must be fixed first?

It correlates assets, microservices, SBOM components, APIs, findings, vulnerability intelligence and sensitive data into a single risk picture, then tracks remediation to completion.

What ATLAS is not
  • Not a replacement for scanners — it orchestrates them through adapters.
  • Not a guarantee of discovering unknown zero-days.
  • Not an AI autopilot — AI output is advisory only.
  • Not authorized to scan anything you do not own or have permission to test.

Security model

  • Authentication: password + optional TOTP MFA, JWT access/refresh tokens,

server-side session revocation, login lockout.

  • Authorization: six roles; permissions checked on every protected endpoint.

Frontend visibility is never treated as authorization.

  • Tenant isolation: every domain record is organization-scoped; foreign IDs

return 404.

  • Scans: explicit authorized scope, authorization reference, no shell execution,

timeouts, cancellation and audit trail.

  • Uploads: size limits, secure XML parsing, no execution.
  • Sensitive data: masked at detection time; raw secrets are not stored.
  • AI: advisory only; cannot modify findings or execute remediation.
  • Risk: deterministic documented scoring (atlas-risk-v1); AI cannot set it.

Read the full model: [docs/security-model.md](docs/security-model.md).

The app opens on a dashboard: run counters, quick-start tiles, recent scans, a searchable list of every module, environment status and key coverage. The sidebar filter (Ctrl+F) narrows the module list as you type.

Window chrome: the top bar carries the workspace views (Dashboard, History, Settings), A- / A+ buttons that scale every font between 100% and 140% (remembered between launches), a ? button that opens a walkthrough of every part of the app, and a fullscreen toggle (F11, Escape to leave). The interface is dark only.

Press Run scan (or Ctrl+Enter). Results stream into the output pane; click any underlined link to open it in your browser. Ctrl+S exports the current output to a text file, Copy puts it on the clipboard.

Troubleshooting

**The window doesn't open / ModuleNotFoundError: tkinter** — tkinter is not a pip package. On Debian/Ubuntu: sudo apt install python3-tk. On Windows, re-run the python.org installer and keep the "tcl/tk" option.

**ModuleNotFoundError: readline** — not used by Null-Trace. That error comes from the old X-osint script.

SMTP module says "Could not connect on port 25" — most consumer ISPs block outbound 25. Run from a VPS or skip that module.

Subdomains returns 0 from crt.sh — crt.sh rate limits hard and returns 502. HackerTarget usually still answers; wait a minute and retry.

Dark Web Search returns the Ahmia landing page — Ahmia rotates an anti-bot token. Null-Trace fetches the token first; if it still fails you are rate limited — wait.

Tor checkbox fails — the SOCKS port is not open. Open Toolkit → Start Tor (the Expert Bundle is installed at %LOCALAPPDATA%\Programs\Tor), or run tor.exe --SocksPort 9050 yourself. The dashboard shows Tor SOCKS: running once it is up, installed when the binary is present but stopped.

Metadata shows fewer tags than expected — install ExifTool (Toolkit → Install ExifTool, or winget install OliverBetz.ExifTool). The app finds it on PATH or in %LOCALAPPDATA%\Programs\ExifTool, so no reboot is needed after installing.

Port scan needs administrator? No — it uses ordinary TCP connect. Some hosts rate-limit or block SYN-less scans; that's their firewall, not a bug.

The window closed or froze during a scan — fixed in 1.0.x; it was a Tk finaliser running on the worker thread. If it ever happens again, the reason is written to %APPDATA%\Null-Trace\crash.log; attach that file to a bug report.

Scans feel slow — port scanning runs 512 connections at a time and DNS resolution 128 lookups at a time. Lower timeout before widening ranges; a /16 sweep still takes minutes because it is 65,535 round trips, not because of Python.

  1. **ScanMixin.start_scan()** — reads the form and checkbox rows, persists preferences, validates the target/ports/flags, and asks scanning.options.build_command() for a list of arguments (never a shell string).
  2. **ScanMixin._execute_command()** — switches to the Live tab, locks Start, enables Stop, starts the spinner and timer, and launches a daemon thread.

Threading model

Tkinter is not thread-safe — a background thread must never call widget.config() directly. NIGHTHAWK solves this by marshalling every UI change through root.after(0, callable, *args), which queues the callable and executes it on the main thread at the next idle moment. The worker thread only runs subprocess.Popen, reads stdout, and queues callables.

Safety & Security Design

NIGHTHAWK is built to be safe by default — even though it wraps a powerful tool.

GuardWhat it protects against
Blocked Nmap flags-oN, -oX, -oG, -oA, -iL, -iR, --datadir, --stylesheet, --webxml, --resume, --append-output — these could overwrite report files or read arbitrary data, so they are rejected
Port validationExpressions are parsed, bounded to 1–65535, and length-limited before reaching Nmap
List-form command buildingThe command is a Python list, not a shell string — there is no shell=True, so shell injection is impossible
CSV formula-injection guardAny cell beginning with =, +, -, or @ is prefixed with a single quote
HTML escapingEvery user-controlled string is passed through html.escape() before entering the report
Thread-safe UIAll background-thread UI updates are marshalled through root.after(0, …)
Temporary filesNmap's XML output goes to a tempfile.mkstemp() path and is deleted after parsing
Config failure toleranceA corrupted nighthawk_config.json silently falls back to safe defaults

Ghostkey — Activity Telemetry Dashboard

Ghostkey is a Windows desktop utility that records foreground application names, visible window titles, application transitions, and approximate foreground usage time during a session. It displays the activity in a local dashboard and can optionally send a session summary to a Telegram chat configured by the operator.

⚠️ Legal and privacy notice: Ghostkey can reveal sensitive information from window titles, including website names, document names, account identifiers, or other text displayed by an application. Use it only on a device and in a session you own or are explicitly authorized to monitor. Tell affected users what is collected, obtain consent where required, and follow applicable laws, workplace policies, and contractual obligations. This README does not make any deployment automatically lawful and is not legal advice.

What Ghostkey Collects

During a session, Ghostkey samples the active foreground window on supported Windows systems. Depending on what is visible in that window's title bar, records may include:

  • Timestamp of an observed event.
  • Foreground process name, such as brave.exe, chrome.exe, or python.exe.
  • Visible window title, which may identify a website, selected browser tab, document, or application view.
  • Application open/close transitions and estimated foreground duration.

The same trace view in the light theme: timestamped metadata lines above, foreground time per app below.

What It Does Not Intentionally Collect

Ghostkey does not intentionally record keystrokes, clipboard contents, screenshots, microphone audio, or page/document contents. It does not provide a complete browser history and cannot reliably identify every page visited.

Browser limitation: The program samples the foreground window title at polling intervals. Browser titles often describe only the selected tab, and title changes that occur between samples may be missed. It does not enumerate all browser tabs or extract search history. A search term is recorded only if it appears in the sampled visible window title; Ghostkey does not inspect the browser's address bar or page DOM.

How Ghostkey Works

The following flowchart shows Ghostkey's intended session workflow, from startup to final report delivery.

flowchart TD
    A(["Launch Ghostkey"]) --> B["Load configuration and initialize dashboard"]
    B --> C{"Start clicked?"}
    C -- "No" --> C
    C -- "Yes" --> D["Start background activity sampling"]
    D --> E["Sample foreground process and visible window title"]
    E --> F["Timestamp observed activity and detect transitions"]
    F --> G["Update event log, runtime totals, and dashboard"]
    G --> H{"Stop clicked?"}
    H -- "No" --> E
    H -- "Yes" --> I["Signal tracker to stop and finish pending work"]
    I --> J["Compile session timeline and per-app usage summary"]
    J --> K["Save final report locally"]
    K --> L{"Telegram configured?"}
    L -- "No" --> M["Keep report locally and show status"]
    L -- "Yes" --> N["Send final report to configured Telegram chat"]
    N --> O{"Telegram confirms delivery?"}
    O -- "Yes" --> P["Record successful delivery"]
    O -- "No" --> Q["Record error and retain local report"]
    M --> R(["Session finished"])
    P --> R
    Q --> R
Workflow Explained
  1. Launch: Ghostkey loads its saved settings and initializes the dashboard.
  2. Start: Clicking Start begins foreground-application sampling.
  3. Collect: The tracker records supported metadata such as timestamps, process names, visible window titles, and observed application transitions.
  4. Update: The dashboard and local event log are updated with the collected events.
  5. Stop: Clicking Stop signals the tracker to stop and finalize the current session.
  6. Generate: Ghostkey compiles the collected events into a session timeline and an approximate per-application usage summary.
  7. Save: The final report is saved locally before Telegram delivery is attempted.
  8. Send: If Telegram is configured, Ghostkey attempts to send the final report to the configured chat. Check the application's delivery status to confirm the outcome.
Important Limitations
  • This diagram describes the intended workflow; it does not prove that every step works in every code version.
  • Sampling can miss brief foreground-window changes.
  • A browser title is not a complete browser history. Ghostkey cannot guarantee capture of every tab, query, click, or page visited.
  • Telegram delivery depends on network access, valid credentials, Telegram availability, and correct handling of message-size limits.
  • The current tracking implementation relies on Windows APIs. Linux tracking requires a compatible platform-specific backend.

Troubleshooting

Telegram Message Is Not Received
  1. Open the Telegram tab and confirm the bot token and chat ID.
  2. Use Test TG and inspect the error shown by the application.
  3. Confirm the bot is allowed to message the destination chat and that the chat ID is correct.
  4. Check internet connectivity and local trace/log files.
  5. Do not publish the token or a report containing private window titles when asking for help.
Tracking Appears Inactive
  1. Confirm the session status in the dashboard.
  2. Check that the application is running on Windows (or Linux with xdotool installed).
  3. Bring a normal application window to the foreground and wait for the configured polling interval.
  4. Review the trace for errors.
  5. If the application crashes, preserve the error message/traceback and report it without exposing credentials or sensitive window titles.
Report Generation Fails

Keep a backup of the local data directory before attempting repairs. Include the traceback when reporting a bug, but redact Telegram tokens, chat IDs, personal information, and sensitive window titles.

Argus

Argus is a Windows/Linux desktop GUI for recursive subdomain reconnaissance. It chains [subfinder](https://github.com/projectdiscovery/subfinder), [httpx](https://github.com/projectdiscovery/httpx) and [dnsx](https://github.com/projectdiscovery/dnsx) into a repeatable pipeline and adds a results table, session resume, run history and subdomain-takeover checks.

Repository: github.com/r4tnadeepbose/Argus

The application is named Argus; the internal Python package is still recon, which is why python -m recon and the recon/ folder appear below.

Authorized use only. Run this tool only against domains you own or are explicitly authorized to test (for example a published bug-bounty scope). DNS brute forcing and HTTP probing against third-party systems may violate laws, terms of service and hosting policies. You are responsible for the targets you enter.

Usage

  1. Enter a target such as example.com.
  2. Set Cycles (recursion depth) and the Status codes to keep.
  3. Optionally choose a wordlist file; otherwise the built-in list is used.
  4. Toggle Screenshots and Takeover check.
  5. Press Start. Rows appear as hosts are found; double-click a row to open it.
  6. Stop at any time, then Resume to continue where you left off.
  7. Export JSON/CSV or Copy URLs for reporting.

A live run: 7 hosts found, two takeover candidates, cycle 2 in progress.

How the pipeline works
cycle n
  subfinder -d <root> -all        (passive, all unvisited roots)
        │
        ▼
  httpx -mc <codes> -json         (probe: status, title, tech, CNAME, -ss)
        │
        ▼
  dnsx + wordlist under live hosts (chunked, resumable)
        │
        ▼
  resolved names -> next cycle roots

Pipeline output: status codes, host, title and tech per live host, with the takeover verdict highlighted.

Sprinter

Sprinter is a browser-based German vocabulary practice app with two short, replayable game modes:

  • Type Sprint — type German words as they fall down the screen.
  • Sprint Guesser — race a timer to choose the correct translation from four options.

Both modes use the same bundled German-English vocabulary and support A1, A2, B1, or all available levels. The interface uses a minimalist black-and-white theme and adapts to desktop, tablet, and phone screens.

Getting started

Open the online app, or run it locally:

  1. Install Node.js 18 or newer.
  2. Open PowerShell or a terminal in the project directory.
  3. Start the included local server:
   node server.js
  1. Visit <http://localhost:8000>.
  2. Select Type Sprint or Sprint Guesser, choose a vocabulary level and other settings, then start.

No package installation, build step, or frontend framework is required.

Google sign-in setup

The web app opens on a Google sign-in screen. To enable it, create a Firebase project, add a web app, and enable Google under Authentication → Sign-in method. Copy the web app's apiKey, authDomain, projectId, and appId into [firebase-config.js](./firebase-config.js), then add the app's hosting domains (including localhost for local development) under Authentication → Settings → Authorized domains. Firebase's web configuration is client-side configuration, not a private service-account key. This setup applies to the web app only; the Android app retains its existing behavior.

Until a Firebase project is configured, web sign-in stays disabled and the app displays a setup message. The Firebase web SDK is loaded from Google's CDN when configured, so sign-in requires an internet connection.

Security notes

  • firebase-config.js contains browser configuration, including a Firebase API key. This configuration is visible to every visitor by design; restrict the key in Google Cloud Console to the required Firebase APIs and the app's websites. It is not a credential for privileged Firebase Admin access.
  • Never put Firebase Admin SDK service-account JSON, private keys, OAuth client secrets, or other server credentials in this repository, frontend assets, or chat. Service-account JSON filenames matching *firebase-adminsdk*.json and *service-account*.json are ignored by Git.
  • Google sign-in currently gates only the web app's screens. The vocabulary and game run entirely in the browser and are public; this app has no authenticated backend or private user data. Client-side screen checks can be bypassed and must not be used to protect future private data or privileged operations. Those require server-side Firebase ID-token verification and appropriate authorization rules.
  • If a credential is exposed, revoke or rotate it in Google Cloud/Firebase immediately, then review repository history and any deployments where it may have appeared.

  2. Select Start. A short three-second countdown begins.
  3. Type the highlighted word, including its article and spaces where shown.
  4. Clear words to earn points and continue. Missing one word ends the run.
  5. Use End Session to finish early and view your analysis.

Sprint Guesser

Sprint Guesser is a timed, multiple-choice translation game. Each question presents a German or English word and four possible translations.

Set up a quiz
  1. Select A1, A2, B1, or All available levels.
  2. Choose German → English or English → German.
  3. Set Time per word to any positive whole number of seconds. The default is 5 seconds; there is no preset upper limit.
  4. Choose a custom session of 5–100 questions or select Endless.
  5. Select Start Quiz and tap or click an answer before the timer runs out.

Only words in the selected level are used for questions and answer options. The app requires at least four distinct translations in the selected level and direction to start a quiz.

Correct answers increase the correct count and streak. Wrong answers and timeouts increase the missed count and reset the current streak; the quiz continues either way. At the end of a custom session, or when End Session is selected, results show correct and missed counts, accuracy, best streak, and a review of missed words.

Play Again starts another session with the currently selected quiz settings.

Mobile and accessibility

  • Layouts adapt to phone and desktop widths; setup and results screens scroll on short displays.
  • On a phone, tap the Type Sprint input field to open the on-screen keyboard. It accepts typing and corrections; desktop keyboards can type directly.
  • Type Sprint controls have touch-sized targets. Its speed slider is horizontal on desktop and mobile.
  • Sprint Guesser presents four choices in a two-by-two grid on wider screens and a single column on narrower screens.
  • Interactive controls have keyboard focus indicators and accessible labels. Quiz answers can be selected with a keyboard as well as by touch or mouse.

Vocabulary

The bundled [words.json](./words.json) file contains 1,198 German-English entries across A1, A2, and B1. It includes nouns, verbs, verb phrases, adjectives, adverbs, conjunctions, expressions, and other vocabulary.

Each entry has this structure:

{
  "german": "die Entscheidung",
  "english": "the decision",
  "level": "B1",
  "partOfSpeech": "noun"
}

Level labels are practical learner estimates and are not official exam classifications. The app loads the bundled file locally; gameplay and its bundled translations do not depend on a vocabulary API. Type Sprint also includes a smaller built-in fallback vocabulary if words.json cannot be loaded. Sprint Guesser needs the vocabulary file served over HTTP.

Sound and pronunciation

When sound is enabled in Type Sprint, the target word is spoken in German, followed by “This means…” and its English meaning. The sequence repeats while the word remains the target. Speech stops when the target changes, the game is paused, or sound is turned off. Completing a word plays a short chime.

There is no voice selector. The game prefers a matching female voice installed in the browser. If an appropriate browser voice is unavailable, the game requests speech audio from /api/pronounce. Browser voices vary by device, and online speech fallback requires an internet connection. If audio is unavailable, the game displays a brief notice rather than blocking play.

Dictionary definitions

After a Type Sprint word is cleared, the app may request an expanded definition from FreeDictionaryAPI. The bundled English translation remains available if the lookup fails. Dictionary results display source attribution when available, including Wiktionary and its CC BY-SA 4.0 license.

Preferences and local data

When Remember preferences is enabled, Type Sprint settings are stored in the browser's localStorage on that device. They are not synced between browsers or devices. Turning the option off removes the saved settings. The game does not require an account.

Run locally

The included Node server serves the app's static files and the pronunciation route:

node server.js

Then open <http://localhost:8000>. Set a different listening port with the PORT environment variable if needed:

$env:PORT = "8080"
node server.js

The local server binds to 127.0.0.1 and only serves an explicit allowlist of frontend files. It also forwards /api/pronounce requests to the shared pronunciation handler. A basic static server such as python -m http.server can serve the pages, but does not provide this API route.

Opening index.html directly with a file:// URL is not the recommended way to run the app: browsers may block the vocabulary fetch, and the pronunciation API route will not exist. Use node server.js for the supported local experience.

The Android app packages the frontend and vocabulary locally, so both game modes work without a connection. Deployment

The project can be deployed on Vercel as a static frontend with a serverless pronunciation function:

  • Vercel serves index.html, style.css, app.js, vocabulary.js, game.js, quiz.js, and words.json as static assets.
  • [api/pronounce.js](./api/pronounce.js) handles GET requests for speech audio. It accepts text and lang=de|en, validates the input, requests audio from an upstream provider, and returns audio or an explicit error response.
  • The app has no frontend build step and the current pronunciation function requires no project-specific environment variable.

To deploy, import the repository in Vercel or use the Vercel CLI from the project directory. The local Node server is for development and is not required for Vercel hosting.
